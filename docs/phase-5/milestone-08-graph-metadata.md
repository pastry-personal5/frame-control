# Milestone 08: Graph-based metadata

**Phase:** [Phase 5](README.md)
**Status:** planned
**Depends on:** [Milestone 02](milestone-02-h3-t2va.md)'s input-free T2VA runs and conditional handoffs; Phase 4 [Milestone 02](../phase-4/milestone-02-multiple-backends.md)'s durable backend records, [Milestone 03](../phase-4/milestone-03-h3-i2av.md)'s audio/video facts, [Milestone 05](../phase-4/milestone-05-h3-r2av.md)'s reference snapshots, [Milestone 06](../phase-4/milestone-06-h3-color.md)'s artifact roles, and [Milestone 09](../phase-4/milestone-09-job-definition.md)'s per-run backend and pipeline records. Include older Draw Things and H3 history only to the extent its facts were recorded.

## Goal

Export and read trustworthy provenance for a job execution. Starting from an output, a person or tool can follow its recorded producer, actual inputs and handoffs, earlier successful runs across resumes, the immutable job snapshot, and each run's backend. Missing evidence remains visible instead of becoming a guessed link.

## Scope

In scope:

- A Framecontrol-owned, versioned YAML graph document, a checked-in schema, deterministic export, and an offline reader.
- A graph projected on request from a consistent SQLite history snapshot. An authenticated HTTP read produces it; `fc history graph` saves or prints that response.
- `fc graph trace`, which reads a saved `.yaml` graph without `fc serve` or the original database and walks backward from an artifact.
- Successful and unsuccessful runs; original and prepared inputs; ordered H3 reference assets; generated outputs, retained raw/uncorrected/corrected copies, and verified video handoffs; missing or conflicting provenance.
- Forward recording changes needed to make future provenance complete, plus conservative migration and repair of imported resume identities.

Out of scope:

- Graph editing or importing a modified graph into Framecontrol, visual layout, a graph database, automatic sidecars, and replacing SQLite, manifests, or queue snapshots.
- One-off `generate` requests and jobs that have not started an execution.
- Reconstructing history by scanning media, parsing saved commands, or matching filenames or paths alone.
- Downloading media or embedding prompt text, commands, job YAML, credentials, file contents, or free-form media-check notes.
- Duplicating seed, model ID, settings profile, or effective timing controls from execution history. The graph records only the lineage and media facts needed to explain artifacts and their dependencies.

## Format decision

- YAML is the canonical graph format for both the HTTP success response and files. Use `.yaml`, UTF-8, one document, and `application/yaml` for the endpoint. The endpoint does not negotiate or produce graph JSON. Ordinary API errors retain the API's JSON error envelope.
- Use YAML for readable inspection beside YAML job definitions. Accept its extra parser complexity explicitly: version 1 data is limited to string-keyed mappings, sequences, strings, booleans, finite numbers, and null. Reject duplicate keys, aliases, anchors, merge keys, custom tags, multiple documents, implicit dates, cyclic or excessively nested values, and non-finite numbers. Quote strings whose plain spelling could change type. Parse only a bounded file with a restricted safe loader; never use a general object loader. The existing strict job-file YAML reader is a starting point, but its accepted syntax is broader than this graph contract.
- Define the data shape with a machine-readable JSON Schema vocabulary file encoded as YAML under `schemas/`, plus normative field, ID, edge, unresolved-reason, and trace rules and small examples in `docs/graph-format.md`. Version 1 is a closed schema: reject unknown fields instead of silently accepting misspellings. A new field or changed field meaning requires version 2. Validate the parsed data model and graph invariants, not YAML layout or comments. Emit one documented field order and sorted node, edge, and unresolved arrays with a final newline; two exports of unchanged history have identical bytes. Avoid export-time timestamps or facts read from the current filesystem.
- Apply the same limits to export and offline input: at most 10,000 nodes, 30,000 edges, 8 MiB of YAML, and 64 nested collection levels. Reject aliases before construction so an alias expansion cannot evade those limits. Bound scalar and collection counts through the total byte, node, edge, and depth limits; report the first field-specific violation deterministically.
- A saved file is a self-contained account of what the store knew at export time. The offline reader checks structure and internal consistency but cannot prove the file was not edited; editing it forfeits its evidentiary trust. Version 1 does not promise a signature or media existence check.

## Graph contract

- The root mapping contains `schema: framecontrol-provenance-graph`, `version: 1`, persistent `store_id`, `root` (for example `execution:E0012`), `scope`, `complete`, `nodes`, `edges`, and `unresolved`. Generate `store_id` once in a forward-only state migration as 128 random bits encoded by 32 lowercase hexadecimal characters, including for upgraded stores; preserve it across later openings and database copies. Node IDs are stable within that store, and `store_id` distinguishes two stores that both have an `E0012`. Exporting and validation never generate or replace it.
- Node types are `job_snapshot`, `backend`, `execution`, `run`, and `artifact`, with IDs such as `job_snapshot:E0012`, `backend:h3-metal-cli`, and `execution:E0012`. A job snapshot belongs to an execution's saved source text, with the SHA-256 digest of that stored text encoded as UTF-8; never use the mutable live `J...` file. Do not embed the text. An imported execution without saved job text has no invented snapshot and has an unresolved definition reference. Backend nodes identify backend IDs; each run, rather than its whole execution, links to the backend and pipeline recorded by Milestone 09. Older execution-wide backend fields are used only where they unambiguously describe every recorded run.
- IDs use an ASCII grammar documented in `docs/graph-format.md`. They contain only fixed type and role words, canonical `E...` IDs, positive decimal run/ordinal numbers, and registered backend IDs; never interpolate a user-supplied pair name, filename, path, or prompt. Run IDs contain execution ID and run number, for example `run:E0013:3`. Artifact IDs identify a recorded role and owner, for example `artifact:E0012:run:2:output`, `artifact:E0012:run:2:handoff`, or `artifact:E0012:run:2:reference:1:image`. This keeps identity stable even when two artifacts have the same path and avoids a second escaping grammar.
- Paths are properties, never identities. Record full local paths where known and the role, recorded byte size and digest, run outcome, measured video/audio facts, and whether an artifact was verified. Encode every digest as `sha256:` plus 64 lowercase hexadecimal characters and omit it when no digest was recorded; export never calculates one. Combine a recorded output directory and basename only when that location is unambiguous; an imported manifest's current directory is not proof of its original output location. A path records historical evidence, not current file existence; export never opens or hashes media.
- Directed edge types are `uses_job_snapshot` (execution to snapshot), `contains` (execution to run), `uses_backend` (run to backend), `consumes` (run to artifact), `produces` (run to artifact), `derived_from` (copy or handoff artifact to its recorded source artifact), `follows` (run to the verified direct producer of an input), and `resumes_from` (execution to its verified resume-point execution). Every edge joins nodes in the document and has a type-valid pair of endpoints. Run numbers show schedule order; `follows` expresses actual input dependency, so an independent `ref2va` run never follows the previous run merely because it was next.
- Run 1's original image and any temporary prepared copy are separate artifacts. The run consumes the copy it actually received, when that is recorded; the copy derives from the original. A `t2v`, `t2va`, or independent `ref2va` run has no invented frame input; a T2VA run remains input-free even when it follows another run. A `ref2va` run consumes its selected ordered, frozen reference copies, including separate audio fields, with recorded pair/ordinal/digest identities. A later image-conditioned run consumes the preceding verified output or extracted handoff actually used, including a T2VA handoff and across backend and resume boundaries. A corrected output derives from its recorded uncorrected delivery, which derives from its raw child where recorded; a handoff derives from the delivered output that produced it. Do not invent intermediate copies or source relationships for old rows that lack them.
- Include a failed, timed-out, or interrupted run and only artifacts it actually recorded. A failed run cannot gain a successful handoff or a successor dependency merely from a reserved output name. If a successful MP4 has no safe handoff, retain its output artifact and mark the required next-run dependency unresolved if a dependent run was attempted. A missing optional artifact that was never produced does not itself make the graph incomplete.
- An edge across runs or executions requires a durable reference to the actual source artifact and the verified resume/run relationship. Path equality, consecutive run numbers, and an old manifest's `E...` number alone are insufficient. When a required source, definition, role, or identity is absent or inconsistent, retain known nodes and add an `unresolved` entry with a stable `id`, existing `from` node when known, intended `relation`, optional unavailable `target`, and a `reason` from the versioned vocabulary. Version 1 includes at least `missing_job_snapshot`, `missing_backend`, `missing_pipeline`, `missing_artifact`, `missing_artifact_identity`, `missing_source_artifact`, `missing_resume_ancestor`, `ambiguous_imported_resume`, `invalid_recorded_reference`, and `scope_omitted_parent`. The format document defines exactly when each applies and the sort key. Do not put prompts, commands, credentials, or free-form media-check notes in an unresolved entry.
- `complete` is true exactly when `unresolved` is empty; it means required provenance links are accounted for, not that media still exists. Scope-limited omitted parents are unresolved by design. An unresolved entry may name an unavailable target ID but does not create a phantom node or dangling edge.
- A full graph for `E0013` contains all recorded runs and artifacts of that execution, then the complete executions that actually supplied a resume input, recursively. It does not add a merely adjacent execution, a failed intermediate resume attempt that supplied no input, or future descendants. `scope: execution` includes only the target execution and its internal nodes and edges; each required external parent becomes `scope_omitted_parent`. Read the complete selected subgraph in one SQLite read transaction so deletion, pruning, or recording cannot mix two database moments. A deleted or pruned ancestor makes a later export partial; an existing saved YAML file remains unchanged.
- Readers reject unknown versions or fields, malformed IDs, duplicate nodes/edges/unresolved IDs, dangling or type-invalid edges, invalid owner/role combinations, contradictory artifact producers, causal cycles, invalid completeness, limits, and schema violations with a field-specific error. Define cycle detection over the dependency relations `resumes_from`, `follows`, and `derived_from`, plus the producer reached for a consumed artifact; containment and descriptive edges do not create causality. No earlier graph format exists to migrate.

## Durable evidence and history repair

- Before implementing projection, audit what Phase 4 Milestones 05, 06, and 09 actually persist. Today H3 raw and uncorrected outputs are named in manifests and structured media-check facts, but not dedicated run columns; H3 reference descriptors live in queue snapshots; and backend identity is execution-wide in history recorded before Milestone 09. Milestone 09 now records on each run its `backend`, `pipeline`, `settings_profile`, resolved `knobs` with their sources, the earlier run and role its image came from (`input_run`, `input_role`), and the prepared copy it read (`resized_input`); a run with none of these predates it. Media-check writes can be skipped without stopping a run.
- Add normalized, execution-owned artifact and artifact-relation records before projection. Each artifact record has one stable owner/role/ordinal, optional run, recorded path, optional recorded digest/size/media facts, and verification state. Relations name artifact records, not paths. Record each selected reference copy, the original and prepared input where known, produced output roles, retained raw/uncorrected/corrected copies, and the actual source used to make a handoff. Write a run's required provenance records in the same recorder transaction as the corresponding run transition, so a crash cannot publish an edge whose endpoint was not committed. A manifest, queue snapshot, or optional media check may seed an explicit migration/import, but none is the sole live authority for a new graph edge.
- Backfill older history only from already stored, unambiguous structured facts. Preserve nulls and explicit unresolved entries where a role, source identity, pipeline, or copy relationship was not recorded. Existing manifests may inform a controlled import or repair, but projection never reads them as a second live source and never guesses from a path, command, or filename.
- `executions.resumes` currently stores a local-looking number copied directly from an imported manifest. An imported manifest may receive a different local execution number, so such a link is untrusted. Add explicit history origin, external execution/resume IDs, import-batch identity, and resume-verification state. In a forward migration, preserve the external reference and clear only imported, unverified local links before export can traverse them; native resume links stay verified. The migration does not scan manifests or guess a replacement.
- For a new `fc import-history` call, read and validate all candidates first, reserve their local IDs, and resolve an external resume ID only when it names exactly one ancestor in that import batch. Duplicate, missing, self, forward, and conflicting references remain unverified. The command may repair an already imported row only when its stored manifest path and imported row facts agree with the currently parsed manifest on the external child ID, external resume ID, start identity, and exactly one ancestor; otherwise it reports the ambiguity and leaves the link unresolved. Never claim that current file content is the original import evidence, link to a coincidentally equal local number, or silently repair during graph export.
- Use execution rows, per-run rows, and durable provenance facts in one consistent read. The artifact/input records serve history, not a second mutable graph store. History deletion and retention may remove rows; a missing target returns not found, and a missing ancestor is unresolved. Graph export itself does not prune, start a backend, acquire the run lock, or mutate history beyond a one-time schema migration on opening an older store.

## Production and consumption

- Add one `state` read that returns the bounded graph evidence inside a deferred SQLite read transaction, and a shared `services` projection over it; do not let `services` issue piecemeal SQL reads. Put pure YAML parsing/emission, format validation, and tracing below `services` within the existing dependency direction. Refuse a missing target, a one-off execution, and an actively running target until it is settled. Export terminal succeeded, failed, interrupted, and parked jobs. Distinguish a stale `running` row with no live runner using the existing history recovery convention, rather than acquiring the run lock for graph reads.
- Add authenticated `GET /v1/executions/{id}/graph` with `scope=full` by default and `scope=execution` as a bounded fallback. On success return the canonical YAML bytes and `application/yaml`; on validation, size, state, or not-found errors use the normal API error shape. Bound the result to 10,000 nodes, 30,000 edges, and 8 MiB of emitted YAML; refuse an over-limit full graph rather than truncate it. The execution scope contains only the target and explicit unresolved parent references.
- Add `uv run fc history graph E0012 --output provenance.yaml` with the existing authenticated API client, server options, `--scope full|execution`, and `--force`; `fc serve` is required. With no `--output`, write the response bytes exactly once to stdout, including its final newline. With `--output`, refuse an existing file, directory, or symlink unless `--force` names a regular-file destination; create a mode-`0600` temporary file with exclusive creation in the destination directory, write and sync it, then atomically rename it and sync the directory where supported. Clean up only the temporary file created by this invocation. Do not transform or reserialize the API response, so API and CLI bytes match.
- Add `uv run fc graph trace provenance.yaml --from artifact:E0012:run:2:output`. Read no more than 8 MiB plus one sentinel byte, reject a file that exceeds the limit rather than accepting its prefix, parse and validate the entire graph before tracing, then print the deterministic text form specified in `docs/graph-format.md` and pinned by golden tests. Traverse backward through derivation, the producing run, that run's consumed artifacts, its snapshot and backend, and resume dependencies. Order equal-depth branches by edge type and ID, mark a shared node on later visits without expanding it again, and show every applicable unresolved stop. Never resolve a path or consult SQLite or the network. Require `--from` to name an artifact node present in the graph; malformed, absent, or non-artifact IDs are distinct field-specific errors.
- Document the YAML contract, direct API use, CLI commands, full-path disclosure, edited-file trust limit, historical gaps, and retention effects in `docs/graph-format.md`, the user guide, and architecture when implementation lands. The TUI need not draw a graph in this milestone.

## Acceptance criteria

- API and CLI produce identical, deterministic version 1 YAML for a settled job. Run and artifact IDs stay unique across executions, and per-run backend and pipeline facts survive mixed chains.
- Starting at an output, offline trace follows only recorded causal inputs through producers, reference copies, job snapshots, and backends. Identical filenames or paths do not merge unrelated artifacts; independent `t2va` and `ref2va` runs do not gain false predecessor edges, while an actual T2VA handoff is traced to its producer.
- Failed or interrupted runs do not acquire successful handoffs. Missing old identities, pruned ancestors, and ambiguous imported IDs appear as reasoned unresolved references; trace stops without claiming missing evidence.
- A malformed, ambiguous, unknown-field, wrong-version, internally inconsistent, too-deep, or oversized YAML file is refused with a useful field-specific error. Export and offline reading enforce the same graph limits. The reader works without a server or database and never treats an edited file as verified by structure alone.
- Export does not modify settled history or write a sidecar unless requested. Full-path exposure and retention/deletion behavior are documented; existing Draw Things and H3 facts appear only where recorded. `make check` passes when the implementation lands.
